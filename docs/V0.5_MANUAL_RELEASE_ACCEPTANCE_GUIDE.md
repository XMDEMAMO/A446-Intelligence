## 2. 开始前的硬性前提

### 2.1 冻结一个可追溯的候选提交

开始外部验收前，先确认工作树没有未提交改动。外部验收必须绑定到一个不可变的完整 Git SHA；否则服务器上验证的代码与报告中的 `releaseHead` 无法对应。

先在开发机执行：

```powershell
cd "E:\GitHub\A446 Intelligence"
git status --short --branch
git diff --check
git diff --stat
```

逐项审查改动后再提交。建议使用 `git add -p` 或显式列出文件，不要直接把所有未跟踪文件加入提交。`docs/V0.5_REMAINING_WORK_HANDOFF.md` 是用户提供的交接文件，是否纳入版本应单独决定。

提交后记录候选 SHA：

```powershell
git rev-parse HEAD
git status --short --branch
```

要求：

- `releaseHead` 使用完整 40 位 SHA。
- 预发布服务器部署的必须是同一个 SHA。
- 验收中又修改代码时，原外部证据作废；生成新 SHA 后重新验证受影响项目。
- 推送、合并和部署是单独的发布决定，不因本手册自动获得授权。

### 2.2 准备隔离预发布环境

至少准备：

- 一台可通过 SSH 管理的 Ubuntu/Debian 服务器和 sudo 权限；
- 一个仅用于预发布的域名，DNS A/AAAA 指向该服务器；
- 只开放公网 80/443，PostgreSQL 5432 和 Hub 8787 只监听回环地址；
- 独立的预发布数据库、Artifact 目录、管理员和 Worker 凭据；
- 两个完整 release 目录：当前候选版本和可回退的上一版本；
- 两台已通过官方方式登录 Provider 的设备；
- 仓库外、权限受控的证据目录。

首次搭建服务器时，先完整执行 [单台预发布服务器配置教程](STAGING_SERVER_SETUP_GUIDE.md)。目录、Caddy、systemd 和恢复脚本的规范以 [部署与回退样例](../deploy/README.md) 为准。

### 2.3 建立证据文件

复制示例到仓库外，不能把凭据放进去：

```powershell
New-Item -ItemType Directory -Force "D:\A446-Evidence" | Out-Null
Copy-Item `
  "E:\GitHub\A446 Intelligence\docs\V0.5_RELEASE_EVIDENCE.example.json" `
  "D:\A446-Evidence\v0.5-release-evidence.json"
```

把 `baseSha` 和 `releaseHead` 改成实际完整 SHA。每一项只有在实际执行并保留证据后才能写成 `passed`。时间使用 ISO 8601 UTC，例如 `2026-09-23T08:30:00Z`。

## 4. HTTPS 与 WSS 现场验收

### 4.1 核对 DNS、监听和防火墙

在独立网络的电脑上检查域名：

```bash
nslookup staging.example.com
curl -I https://staging.example.com/
```

在服务器上检查监听：

```bash
sudo ss -ltnp | grep -E ':(80|443|8787|5432)\b'
```

预期：

- 80/443 由 Caddy 对公网监听；
- 8787 只在 `127.0.0.1` 或 `::1`；
- 5432 只在回环地址或 Unix socket；
- 浏览器打开 HTTPS 地址没有证书警告。

### 4.2 配置并验证 Caddy

以 [Caddyfile.example](../deploy/Caddyfile.example) 为基线，替换真实域名和静态文件路径。不要删除 `/api` 前缀处理、`/worker` WebSocket 代理或安全响应头。

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
sudo systemctl status caddy --no-pager
sudo journalctl -u caddy -n 100 --no-pager
```

HSTS 默认保持关闭，只有域名和所有子域的 HTTPS 策略已经稳定后再启用。不要为了排错关闭浏览器或 Worker 的证书校验。

### 4.3 从公网执行无凭据验证

在能访问预发布入口的独立网络执行：

```bash
cd '/path/to/a446-candidate'
node scripts/deploy/verify-public-endpoint.mjs https://staging.example.com
```

该脚本应通过以下项目：

- `/api/health` 返回 `ok=true`；
- 未登录 API 返回 401；
- `/worker` 返回预期的认证或 Upgrade 边界；
- CSP、`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 存在；
- HTML 为 `no-store`；
- 带指纹的静态资源为一年 immutable 缓存。

HSTS 仍未启用时脚本只会给出警告；报告中应如实记录。

### 4.4 手工检查安全 Cookie

1. 使用预发布管理员登录。
2. 打开浏览器开发者工具 → Application/Storage → Cookies。
3. 找到 `a446_session`，确认 `HttpOnly`、`Secure`、`SameSite=Strict`。
4. 页面刷新后仍保持登录。
5. 正常退出后，受保护 API 再次返回 401。
6. 不要截图或复制 Cookie 值。

### 4.5 验证实际 WSS

在服务器之外的一台 Worker 设备上，配置：

```json
{
  "hubUrl": "wss://staging.example.com/worker",
  "authTokenEnv": "A446_WORKER_TOKEN",
  "authRequired": true,
  "artifacts": {
    "centralStore": true,
    "apiUrl": "https://staging.example.com"
  }
}
```

启动一个专用测试 Worker，确认 Web 中显示相同 `agentId` 和 `deviceId` 在线。不得改回 `ws://`、关闭 TLS 校验或复用其他 Worker 的 Token。

通过后，将 `httpsWss` 记录为 `passed`，证据至少写明候选 SHA、域名、验证时间、脚本结果、证书颁发对象和成功上线的非敏感 Agent ID。

## 5. systemd Worker 异常退出与重连验收

该步骤验证目标服务器上的 `Restart=on-failure`，不能用 `systemctl restart` 代替异常退出。优先使用一个可丢弃的专用测试 Worker；验证服务管理本身时可以使用 Mock Adapter，真实模型流程另在第 8 节执行。

设定本次单位名称：

```bash
export A446_WORKER_UNIT='a446-worker@executor-01.service'
```

### 5.1 记录重启前状态

```bash
sudo systemctl status "$A446_WORKER_UNIT" --no-pager
sudo systemctl show "$A446_WORKER_UNIT" \
  -p ActiveState -p SubState -p MainPID -p NRestarts
OLD_PID="$(sudo systemctl show "$A446_WORKER_UNIT" -p MainPID --value)"
printf 'old pid: %s\n' "$OLD_PID"
```

同时在 Web 中确认该 Worker 在线，记录 Agent ID、device ID 和时间。

### 5.2 制造一次受控异常退出

确认 PID 非空且大于 1，再执行：

```bash
test -n "$OLD_PID" && test "$OLD_PID" -gt 1
sudo kill -KILL "$OLD_PID"
```

等待 systemd 自动恢复，不要手工启动：

```bash
for attempt in $(seq 1 30); do
  NEW_PID="$(sudo systemctl show "$A446_WORKER_UNIT" -p MainPID --value)"
  STATE="$(sudo systemctl is-active "$A446_WORKER_UNIT" || true)"
  if [ "$STATE" = active ] && [ -n "$NEW_PID" ] && [ "$NEW_PID" != 0 ] && [ "$NEW_PID" != "$OLD_PID" ]; then
    printf 'worker restarted: %s -> %s\n' "$OLD_PID" "$NEW_PID"
    break
  fi
  sleep 1
done

sudo systemctl show "$A446_WORKER_UNIT" \
  -p ActiveState -p SubState -p MainPID -p NRestarts
sudo journalctl -u "$A446_WORKER_UNIT" --since '-5 minutes' --no-pager
```

### 5.3 验证应用层重连

1. Web 中同一 Agent 先离线后重新上线。
2. 没有出现第二个幽灵 Agent 或身份不匹配。
3. 新建一个可丢弃的小任务，确认该 Worker 能领取并完成或被正常取消。
4. 如果要验证运行中任务恢复，只使用无副作用、可安全重试的任务；记录旧/新 Attempt ID 和最终状态。

通过后，`workerRestart` 证据应包含旧/新 PID、`NRestarts`、日志时间范围、Agent ID、重连耗时及验证任务 ID。日志中若包含秘密，先脱敏再保存。

## 6. PostgreSQL 与 Artifact 成对备份/恢复演练

恢复是本手册风险最高的步骤。推荐恢复到专用演练数据库和独立 Artifact 目录，不覆盖正在使用的预发布数据。只有确认预发布环境本身可丢弃，并明确批准维护窗口时，才做原位恢复。

### 6.1 创建恢复前哨数据

在当前预发布环境中创建一个可识别的任务和小型 Artifact，并记录：

- 任务 ID；
- Artifact ID；
- Artifact 的 SHA-256；
- 一个待处理人工介入 ID（如有）；
- 创建时间。

这些数据用于证明数据库记录和文件内容来自同一个备份点。

### 6.2 创建一致性备份

停止新任务，等待必要任务结束，并通知远程 Worker 暂停。然后在服务器执行：

```bash
sudo systemctl stop a446-server-hub
sudo systemctl is-active a446-server-hub || true
sudo ss -ltnp | grep ':8787\b' || true

sudo install -d -o a446 -g a446 -m 0700 /var/backups/a446
sudo -u a446 -H bash
set -euo pipefail
set -a
. /etc/a446/server-hub.env
set +a
cd /srv/a446/current

PGDATABASE="$A446_DATABASE_URL" psql -Atqc \
  "select current_database(), inet_server_addr(), inet_server_port();"
realpath "$A446_ARTIFACT_ROOT"
```

人工确认输出确实是预发布数据库和预发布 Artifact 目录，再继续：

```bash
export A446_MAINTENANCE_CONFIRMED=yes
bash scripts/deploy/backup-server.sh /var/backups/a446
unset A446_MAINTENANCE_CONFIRMED A446_DATABASE_URL A446_ARTIFACT_ROOT
exit
```

从 `Backup complete:` 输出复制本次准确目录，例如：

```bash
export BACKUP_DIR='/var/backups/a446/a446-20260923T083000Z'
test -f "$BACKUP_DIR/COMPLETE"
test ! -e "$BACKUP_DIR/INCOMPLETE"
test -f "$BACKUP_DIR/a446.dump"
test -d "$BACKUP_DIR/artifacts"
(cd "$BACKUP_DIR" && sha256sum --check SHA256SUMS)
cat "$BACKUP_DIR/MANIFEST.txt"
```

检查完成后可重新启动当前预发布 Hub：

```bash
sudo systemctl start a446-server-hub
curl --fail http://127.0.0.1:8787/health
```

### 6.3 准备独立恢复目标

使用独立角色、数据库和 Artifact 根目录。数据库密码通过交互提示输入，不写入命令历史：

```bash
sudo -u postgres createuser --pwprompt a446_restore_user
sudo -u postgres createdb --owner=a446_restore_user a446_restore_rehearsal
sudo install -d -o a446 -g a446 -m 0750 /var/lib/a446/restore-rehearsal
```

用 `sudoedit` 创建临时 `/etc/a446/restore-rehearsal.env`：

```text
A446_DATABASE_URL=postgresql://a446_restore_user:<URL编码密码>@127.0.0.1:5432/a446_restore_rehearsal
A446_ARTIFACT_ROOT=/var/lib/a446/restore-rehearsal/artifacts
```

```bash
sudo chown root:a446 /etc/a446/restore-rehearsal.env
sudo chmod 0640 /etc/a446/restore-rehearsal.env
```

再次核对目标数据库名和 Artifact 路径。它们不得是活动预发布目标。

### 6.4 恢复备份副本

```bash
sudo -u a446 -H bash

set -a

set +a

```

把 `BACKUP_DIR` 替换为 6.2 节已经校验过的实际备份绝对路径。只有数据库输出为 `a446_restore_rehearsal`、Artifact 输出为 `/var/lib/a446/restore-rehearsal/artifacts`，且该备份含 `COMPLETE` 时才继续：

```bash
export A446_MAINTENANCE_CONFIRMED=yes
export A446_RESTORE_CONFIRMED=yes
bash scripts/deploy/restore-server.sh "$BACKUP_DIR"
unset A446_RESTORE_CONFIRMED A446_MAINTENANCE_CONFIRMED

cd apps/server-hub
npm run migrate
```

使用记录的任务和 Artifact ID 验证数据库：

```bash
PGDATABASE="$A446_DATABASE_URL" psql -x -c \
  "select task_id, status, created_at from tasks where task_id = '<前哨任务UUID>';"

PGDATABASE="$A446_DATABASE_URL" psql -x -c \
  "select artifact_id, status, byte_size, sha256, storage_key from artifacts where artifact_id = '<前哨Artifact ID>';"
```

从查询结果复制 `storage_key`，先确认它是相对路径且不包含 `..`，再验证文件：

```bash
export RESTORED_STORAGE_KEY='<查询得到的相对 storage_key>'
test "${RESTORED_STORAGE_KEY#/}" = "$RESTORED_STORAGE_KEY"
case "$RESTORED_STORAGE_KEY" in *'..'*) exit 1;; esac
sha256sum "$A446_ARTIFACT_ROOT/$RESTORED_STORAGE_KEY"
```

输出必须与备份前记录的 SHA-256 一致。还应查询待处理介入是否存在：

```bash
PGDATABASE="$A446_DATABASE_URL" psql -x -c \
  "select intervention_id, status, created_at from human_interventions where intervention_id = '<前哨介入ID>';"
```

退出服务账户 shell，并保留证据。演练数据确认无用后，由数据库管理员删除专用恢复数据库/角色和 Artifact 目录；删除前再次核对绝对路径，不能删除活动 `/var/lib/a446/artifacts`。

`backupRestore` 通过标准：备份完整标记与校验和通过，数据库前哨记录存在，Artifact 文件存在且 SHA-256 一致，恢复目标与活动环境隔离，整个过程没有使用生产库。

### 7.1 准备两个完整 release

假设：

```bash
export CANDIDATE_RELEASE='<候选 release 目录名>'
export PREVIOUS_RELEASE='<上一 release 目录名>'
```

检查两个目录都有后端入口和 Web 构建：

```bash
test -f "/srv/a446/releases/$CANDIDATE_RELEASE/apps/server-hub/src/server-hub-cli.mjs"
test -f "/srv/a446/releases/$CANDIDATE_RELEASE/apps/web/dist/index.html"
```

```bash
diff -u \
  <(cd "/srv/a446/releases/$PREVIOUS_RELEASE/apps/server-hub/migrations" && printf '%s\n' *.sql | sort) \
```

```bash
bash scripts/deploy/switch-release.sh "$PREVIOUS_RELEASE"
unset A446_SERVICES_STOPPED A446_MAINTENANCE_CONFIRMED
readlink -f /srv/a446/current
```

- migration 集合完全兼容时，启动旧版本并验证。
- migration 不兼容时，先用第 6 节切换前的同一份成对备份恢复数据库和 Artifact，再启动旧版本。
- 不得删除 migration、手工修改 migration 记录或只回退代码不处理不兼容 schema。


`versionRollback` 通过标准：候选和上一版本均能被明确激活；回退后健康、公网入口和至少一个可丢弃工作流正常；schema 不兼容时成功恢复了同一维护窗口的数据库与 Artifact；最终环境重新回到候选版本。

## 8. 真实 Codex/Antigravity 双设备验收

完整的设备操作和结果模板也可参考 [账号 D 最终集成手工验证操作手册](账号D最终集成手工验证操作手册.md)。

### 8.1 设备与身份分配

推荐：

- 设备 1：Codex Planner 与 Codex Executor；
- 设备 2：Antigravity/Gemini Reviewer；
- 每个逻辑 Agent 使用不同 `agentId`、Worker Token、`stateFile` 和 `workspace`；
- 同一设备可以共用 `deviceId`，但不能共享 Agent 状态或模型会话；
- 两台设备均使用 `wss://staging.example.com/worker` 和 `https://staging.example.com` Artifact API。

设备所有者亲自确认官方客户端已经登录并能看到预期模型。不要迁移账号目录、Cookie、浏览器资料或登录 Token。

### 8.2 为每个 Worker 创建一次性凭据

在服务器的受保护 shell 中分别执行，命令输出的 Token 只显示一次：

### 8.3 启动三种角色

先在各设备复制对应模板；设备 1 需要两个独立 Codex 配置，设备 2 需要一个 Antigravity 配置：

## 11. 失败时立即停止的情况

遇到以下任一情况，不要继续尝试或把结果写成通过：

- 服务器 SHA 与 `releaseHead` 不一致；
- 无法确认数据库或 Artifact 目标，或目标疑似生产环境；
- 8787/5432 暴露公网；
- HTTPS 有证书警告，Worker 只能关闭 TLS 校验后连接；
- 恢复备份缺少 `COMPLETE`、`SHA256SUMS` 或校验失败；
- 旧代码与新 schema 是否兼容无法确认，却准备只回退代码；
- systemd 没有自动重启，必须人工启动 Worker；
- Worker 只能复用其他设备的身份或 Token；
- Artifact SHA-256 不一致；
- 真实模型调用没有当次明确授权，或达到额度停止条件；
- 证据包含秘密信息。

保留错误时间、非敏感摘要和相关 ID，再交给最终集成人分析。
